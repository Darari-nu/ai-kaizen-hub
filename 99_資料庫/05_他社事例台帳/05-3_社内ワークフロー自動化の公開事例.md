## 1-1. ADKマルチエージェントでkintone承認を自動化した設計と自動評価（eval）の実践

| 項目 | 内容 |
|---|---|
| 公開日 | 2026.08.05 |
| 著者 | Hiroshi Toyama（記名あり。本文では「DeNA でエンジニアをしている外山です」） |
| タグ | #adk #ai-agent #multi-agent #ai #llm #gemini #vertex-ai #kintone #evaluation #workflow-automation |
| 出典URL | https://engineering.dena.com/blog/2026/08/kintone-approve-agent-adk-eval/ ／ 一次 ／ 2026-08-15 |

**何を自動化したのか**
社内の**ツール利用申請ワークフロー（kintoneで運用）**で、**承認前に人間が行っていた3つの確認作業**。

1. 予算内かどうか（予算残額シートとの突き合わせ）
2. 申請されたツール名がマスターに存在するか
3. 「法務確認は不要」という選択が本当に妥当か

本文の表現: レコードを読んで別のシート／マスターと照合するだけの**定型作業**だが「申請件数が増えると
地味に時間を取られます」。判断基準がはっきりしていて件数も多い作業をエージェントに寄せた、という位置づけ。

**使った技術（本文に書かれている構成）**

| 層 | 実物 |
|---|---|
| LLM | **Gemini 2.5 Pro**（4エージェント全てに同一モデルを指定） |
| エージェント基盤 | **Google ADK（Agent Development Kit）** |
| 推論の実行環境 | **Vertex AI Agent Engine**（マネージド。「推論の実行基盤を自前で運用せずに済む」ため選定） |
| Webhook受け | **Cloud Run**（kintoneのステータス変更Webhookを受ける） |
| IaC | **Terraform**（記事ではインフラ詳細は割愛と明記） |
| CI/CD | Cloud Run と Agent Engine を**1本のパイプライン**で。mainブランチpush=dev環境、バージョンタグpush=prod環境 |
| 構成 | `root_agent`（ルーターに徹する）＋サブエージェント3つ（`budget_check` / `tool_name_suggest` / `legal_check`）。サブエージェントごとに**使えるtoolを絞る** |
| データ整形 | kintoneレコードを**除外フィールドリストで削ぎ落としてYAML化**してからプロンプトへ。法務確認側は逆に**許可リスト方式**（判定に使うフィールドが十数個に限られるため） |
| 前段フィルタ | LLMを呼ぶ前に3段階の軽量チェック（イベント種別 → ステータス値 → 業務フラグ）。「モデルより手前でフィルターするのがもっとも効くコスト最適化」 |
| 評価 | `adk eval`（オフライン回帰テスト） |

**技術選定の理由（本文の記載）**: ①社内でGoogle Cloud基盤とGeminiを標準的に使っていてそのまま乗せられる
②Agent Engineにデプロイすれば実行基盤を自前運用せずに済み運用負荷が低い。

**公表されている数値**

| 項目 | 値 |
|---|---|
| evalのテストケース数 | **3エージェント合計27ケース** |
| FAIL件数 | **7件**（すべて `final_response_match_v2` のみが原因） |
| 使ったメトリクス | 5つ（`tool_trajectory_avg_score` / `rubric_based_tool_use_quality_v1` / `rubric_based_final_response_quality_v1` / `hallucinations_v1` / `final_response_match_v2`） |
| judgeのサンプリング回数 | `rubric_based_final_response_quality_v1` と `hallucinations_v1` は**1ケースあたりjudgeモデルを5回サンプリング**。フルセット実行に数分 |
| 削減時間・削減件数・コスト | ⬛非公開（**記事本文に一切記載なし**。DeNAはこの案件の効果を数値で公表していない） |

**つまずいた点・失敗談（本文に節が立っている）**
- 見出しがそのまま「**adk evalでハマった話：final_response_match_v2は信用しない方がよい**」。
- 27ケース中7件がFAILしたが「実害のあるバグではなく、原因は完全にメトリクス側の設計にありました」。
- 原因: このメトリクスは**最後のテキストターンだけ**を見る。しかし3エージェントとも判定の中身は
  `post_kintone_comment` ツール呼び出しの引数に入る。最終文が「コメント全文の繰り返し」か
  「投稿しました、という完了報告」かは**LLMのサンプリングでブレる**ため、コードを変えずに再実行しても
  PASS/FAILがひっくり返るノイズ源になっていた。他4メトリクスは同じ実行で安定してPASS。
- 対処: 3つの `test_config.json` すべてから `final_response_match_v2` を除外し、
  判定内容は `rubric_based_final_response_quality_v1` のルーブリックで評価（評価対象を最終応答テキストに
  限定せず、ツール呼び出しの中身まで見させる書き方にした）。
- 教訓（本文の言い方）: 出力がツール呼び出しに乗るエージェントに `final_response_match_v2` は不向き。
  避けるべきは「期待する最終応答テキストを固定して一致で採点するeval」、作るべきは
  「ツール呼び出しの引数や順序を検証するeval」。
- もう一点: instructionは緩い自然文ではなく**番号付きの厳密な手順**として書いている
  （「出力が実際の承認判断に直結するシステムでは、分岐をモデルの都度の解釈に委ねない」）。

**紐付けタグ**: ネタ帳「ノーコード業務DBの定番3種アプリを自作する」／「承認ワークフローのAI自動化」

## 1-2. 社内申請が行われるたびにプロンプトがどんどん育つAIエージェントを支えるDevin

| 項目 | 内容 |
|---|---|
| 公開日 | 2026.06.26 |
| 著者 | Hiroshi Onodera（本文「IT本部 AI・データ戦略統括部 データ基盤部 AIジャーニー推進グループ…小野寺」） |
| タグ | #devin #ai-agent #ai #prompt-engineering #automation #continuous-improvement #kintone #langfuse |
| 出典URL | https://engineering.dena.com/blog/2026/06/devin-prompt-improvement-cycle/ ／ 一次 ／ 2026-08-15 |

**何を自動化したのか（2階建て）**
1. **1階**: 外部ツール（本文の例示は Claude / Linear / Cursor）の**利用申請の記入を代行するAIエージェント**。
   ユーザーと対話しながら kintone の申請フォームに記入し、**申請の下書きを作成**する。
   本文の課題認識: 入力項目が多く、**フィールド間の依存関係**（ある値によって別フィールドの必須状態が変わる）が
   入り組んでいて「人が埋めるだけでもそれなりに骨が折れる」。
2. **2階（この記事の主題）**: その申請エージェントの**プロンプトを毎週AIに自動改善させる仕組み**。
   **差し戻し**コメントと会話ログを読み、プロンプトを直し、Draft PRを出すところまでをDevinが行う。

**使った技術**

| 層 | 実物 |
|---|---|
| 申請フォーム | **kintone（サイボウズ）** |
| 申請エージェントのLLM | **Claude** |
| 改善役のAI | **Devin**（Playbook＋Scheduled Sessions） |
| 観測基盤 | **Langfuse**（OpenTelemetry経由でトレース記録） |
| スケジュール | cron式 `0 9 * * 1` = **毎週月曜9時** |
| Playbookの置き場所 | リポジトリ内の**Markdownファイル**（「Claude の Skill に相当」と本文が説明） |

**毎週月曜にDevinがやる5ステップ（本文の列挙）**: ①会話ログと差し戻しコメントからつまずきを集める
②繰り返し出ているものを数件に絞る ③プロンプトの該当箇所を直す ④テストを通す ⑤Draft の Pull Request を出す。
人がやるのは PR のレビューとマージだけ。

**公表されている数値**

| 項目 | 値 |
|---|---|
| Devin の全社導入規模 | **2,000人以上が使える状態**（DeNA全社導入） |
| 2026年6月のPR本数 | **4本**（6/1・6/8・6/15・6/22 の各週に1本ずつ） |
| 1本あたりの変更量 | **数行から十数行** |
| 同一テーマの収束に要した週数 | **3週**（法務確認の選択ミス。6/1の週に修正 → 6/8・6/15と続き同じ箇所に3週かけて修正。6/22の週も上位テーマとして再出現） |
| 削減時間・コスト | ⬛非公開（**記事本文に記載なし**） |

**つまずいた点・失敗談（濃い）**
- 「差し戻しのたびに、プロンプトを手で直していた」— 直すとそのパターンは直るが、
  しばらくすると**少し違うパターンでまた差し戻される**。この手直しがずっと続いていた（＝自動化の動機）。
- **つまずきの多くは「書かれていなかった基準」**。運用開始から1ヶ月ほどの時点では、
  「エージェントが間違った判断をした」より「**判断基準がそもそもプロンプトに書かれていなかった**」が
  ほとんどだった。追記したのは数行で、「人間なら暗黙にやっている判断を、言葉にして渡しただけ」。
- **1本の修正で完結したケースはほぼなかった**。「実際に申請が行われてはじめて出てくるパターンがあって、
  最初から全部書ききることはなかなか難しいようです」。
- キーワード抽出の誤爆: 会話ログを「違います」「修正して」「ではなく」「やり直し」等で拾うと
  **文脈違いも一緒に拾う**（エージェントへの指示文自体に「ではなく」が入っている等）。
  対処＝**同じ問題が一定回数以上くり返し出たものだけを採用**する閾値フィルタ。
- **人間が握っているところ（ガードレール5点）**: ①直していいのはプロンプト本文だけ（ロジックには触らせない）
  ②1回の変更行数に上限 ③テストが全部通らなければPRを作らせない ④必ずDraft・自動マージしない
  ⑤最後は人間がレビューしてマージ。加えて**認証まわり・インフラ設定は「AIが触らない領域」として対象外**。
- Playbook内にも文章として歯止めを書いている: 「テスト書き換え禁止」「draft 必須」「マージ前デプロイ禁止」。
- 横展開の設計: kintoneから**フォーム定義を実行時に取得する設計**にしたため、
  対応リストに登録するだけで申請種別を増やせる。

**紐付けタグ**: darari本人の一次体験ヒアリング（申請差し戻し・根回し失敗）と真正面から対応する事例。

## 1-3. ツール導入時における法務確認のリードタイム削減 ← **数値がいちばん強い**

| 項目 | 内容 |
|---|---|
| 公開日 | 2026.01.15 |
| 著者 | Yuki Narita（本文「IT本部IT戦略部テクニカルオペレーショングループの成田です」） |
| タグ | #llm #ai #corporate-it |
| 出典URL | https://engineering.dena.com/blog/2026/01/legal-check-automation/ ／ 一次 ／ 2026-08-15 |

**何を自動化したのか**
SaaS等を社内導入する際の「**ツール利用申請**」（kintoneアプリ）のうち、**法務部門による法務確認**。
新フロー: ①kintoneアプリで申請 → ②**LLMがツール利用規約をチェックしサマリを作成** →
③利用ケースのリスク度合いを自社基準で判定 → ④申請者所属部門の承認者がLLMチェック結果のサマリを確認 →
⑤類型的にリスクの低いツールは**承認者の承認のみで利用開始**／懸念があれば法務担当者（人）へエスカレーション。

**使った技術**

| 層 | 実物 |
|---|---|
| フォーム／ワークフロー | **kintone** |
| 規約チェック | **LLM**（モデル名は本文に記載なし。「入力データが学習に利用されないセキュアな環境」と明記） |
| プロンプト運用 | **法務担当者自身が適宜チューニング**して継続的に精度改善できる仕様 |
| フォーム制御 | **JavaScript** でフィールドの表示/非表示・入力可否を制御し、ヒアリングのフロー分岐をフォーム上で再現 |
| 台帳 | 別のkintoneアプリ「**ツールマスタ**」（過去にリスク確認したツール情報を一元管理） |
| 統合 | 「ツール利用申請」と「購買・ライセンス付与申請」の**2アプリを1つに統合**し「ツール利用・購買申請」へ |

**公表されている数値（本文の表そのまま）**

| 計測項目 | 旧「ツール利用申請」<br>2025/09/01〜09/30 | 新「ツール利用・購買申請」<br>2025/10/01〜10/31 | 変化 |
|---|---|---|---|
| 総待ち時間 | **21,306時間** | **5,210時間** | **→76%削減** |
| 法務確認待ち時間 | **17,695時間** | **1,530時間** | **→91%削減** |

| 件数の内訳 | 旧 | 新 |
|---|---|---|
| 法務担当者（人）による確認 | **70件** | **29件** |
| LLMによるリスク確認 | — | **27件** |
| LLMによるリスク確認＋人へのエスカレーション | — | **3件** |

| 1件あたりの待ち時間（人による法務確認） | 旧 **88時間** → 新 **45時間** ／ **→49%削減** |
|---|---|

その他、本文中の数値・事実:
- 施策前、**法務確認プロセスがツール利用申請全体の待ち時間のうち「約8割」を占めていた**。
- 新アプリでは計測期間の**申請のおよそ半数の30件**がLLMによるリスク確認の対象になり、
  うち**3件がエスカレーション、27件はLLMのチェックのみで法務確認を完了**。
- 削減できた要因の説明: リスクの低いケースで、人による法務確認を
  「**LLMチェック＋事業部のツール利用承認者による承認**」へ置き換えたため。

**つまずいた点・今後の課題（本文「今後の課題」節）**
- **LLMチェックが手作業でつながっている**: 申請対応者（人）がkintoneレコードのデータを
  **専用のWebUIに手で入力し、出力結果をkintoneレコードに手動入力**している。
  API連携で自動化して申請対応者の工数を削減することを検討中。
- 「ツールマスタ」の仕様を、ツール利用・購買申請との親和性を高めるために見直し検討中。
- 失敗談としての記述はなし（成功事例の書きぶり）。

**課題分析（施策の前提として書かれている一次のヒアリング結果）**
①利用規約の文章量が非常に多く、リスクチェックを目視で行うのに時間を要す
②申請時に事業部から提供される情報が不十分・分かりづらく、追加ヒアリングと情報整理に時間を費やす。

## 1-6. kintone内製プラグインで350超アプリのカスタマイズをノーコード化した話

| 項目 | 内容 |
|---|---|
| 公開日 | 2026.07.28 ／ 著者 Takashi Irikura（IT本部IT戦略部テクニカルオペレーショングループ） |
| 出典URL | https://engineering.dena.com/blog/2026/07/kintone-plugin/ ／ 一次 ／ 2026-08-15 |

**何を作ったのか**: 「入力制御プラグイン」の**内製開発**。AI不使用。
機能は3分類 ①各フィールドの条件制御（必須/任意/入力不可/非表示の切替）
②ユーザー選択フィールドの制御（1名限定、漢字氏名・メール・所属部署の書き出し）
③レコード再利用時の値クリア。

**数値**
| 項目 | 値 |
|---|---|
| 稼働中のkintoneアプリ数 | **700を超えています**（2026.07時点） |
| プラグイン導入済みアプリ | **350を超えています** |

**なぜ内製したか（＝落とし穴の一次記述、§5に再掲）**
- 高度なカスタマイズにはJavaScriptが必要だが、**社内の全ユーザーが開発スキルを持つわけではない**。
- kintoneの仕様として**スクリプトファイルをアプリにアップロードするには kintone 全体のシステム管理権限が必要**。
  → 一般ユーザーに任せることも、IT戦略部が全部代行することも難しい、という板挟み。
- **有償プラグインも検討した**が、各アプリの運用状況を調査した結果「多くのアプリで求められる機能は限定的」
  と判断し、利用頻度の高い機能に絞って**追加費用なし**で内製する方針にした。

**運用上の制約（本文に明記）**
- 開発に使ったパッケージ（`plugin-uploader` / `plugin-packer` / `create-plugin` /
  `webpack-plugin-kintone-plugin`）は**いずれも開発当時のもので、現在はいくつかが非推奨**。
- **JavaScriptによるカスタマイズとプラグインの併用は不可**としている（競合の可能性のため）。
- プラグインで全要望は満たせず、**複雑な要件には引き続き個別のJavaScript開発も行っている**。

## 1-9. 「使いこなす」より「使いまくる」！情シスの生成AI活用事例10選 ← **失敗談の宝庫**

| 項目 | 内容 |
|---|---|
| 公開日 | 2026.05.28 ／ 著者 Kazuya Ichinohe（IT戦略部 コーポレートオペレーショングループ＝CorpOps） |

**失敗談・つまずき（一次）**
- **AIが自信満々に嘘をつく**: マスタ変更のダブルチェックをAIにやらせたところ、
  **申請内容と全く関係ない法人番号を見つけてきて「合ってます！」**と回答。
  「インターネット上の広範な情報を拾おうとするGeminiの性質が裏目に出てしまった」。

- 動画をNotebookLMにアップできない時がある／動画内の文字列を正確に読み取れないことがある
  → 最新版では**動画を止めて、登録後の画面キャプチャとスプレッドシートの突合方式に変更**。
- **AIに計算させると平気で間違える／ハルシネーションが発生**する
  → 「AI自身にチェックさせるのではなく、**チェックするプログラムを書かせればいい**のでは」に転換
  （見出しは「『計算』させるな『計算機』を作らせろ」）。
- **AIに記事を書かせたら偏った**: 今回の記事の約7割を生成AIが執筆。最初は4000字の
  「それらしい」文章が出たが**過不足や違和感がたくさん**あり、選ばれた事例にも偏りがあった
  （「効率化」「自動化」など**対外的にアピールしやすいキーワードを含むものが多かった**）。
  → Googleカレンダーのアジェンダをインデックスにして指示し直したら偏りが消えた。
- マインドセット2点: 「**使いこなす**」のではなく「**使いまくる**」／
  「**それっぽい出力**」を見抜くには**業務知識**が必要（レビューする人間の業務知識が不可欠）。

**その他の事例（10選の見出しのみ）**: ①OCRとして利用 ②リリースノートの影響調査 ③規格/標準/フォーマットを

⑧「歴戦のプロ」になりきらせて壁打ち ⑨マニュアルから先生を作り出す ⑩議事録から記事を自動生成。

## 2-1. Finatext ─ 既存の承認ワークフローにAIを「担当者」として入れる

| 項目 | 内容 |
|---|---|
| タイトル | SaaSの業務オペレーションを、AIオペレーターに |
| 公開日 | 2026/07/09 ／ 著者 Aka Chin（@chinaka） |
| 媒体 | **Finatext Tech Blog（Zennの企業パブリケーション "Publication Pro"）**＝企業アカウント |
| 出典URL | https://zenn.dev/finatext/articles/7cdf789e37cb38 ／ 一次 ／ 2026-08-15 |

**何を自動化したのか**: 自社のクレジットビジネスプラットフォーム「Crest」の**審査オペレーション**、
題材は「**在籍確認**」（申込者が申告した勤務先に本当に在籍しているか）。
※**社内稟議ではなく、プロダクト側の業務オペレーション**である点に注意（記事化のとき混同しないこと）。

**設計の核（承認ワークフローとの関係がまさに本題）**
- 「業務をまるごとAIに置き換えるのではなく、AIを『**もう一人のオペレーター**』としてチームに入れる」。
- 「『**担当者が申請し、別の人が承認する**』という既存のワークフローに、**AIが担当者として入る**イメージ」。
- AIが判断案を提出すると **Crest側で承認依頼が自動で作られ、別の人間（承認者）が再鑑**する。
  **申請者本人は承認できない**（職務分離）。誰が何を根拠にどう判断したかは**監査ログに残る**。

**使った技術**

| 層 | 実物 |
|---|---|
| LLM／実行環境 | **Claude**（Claude Code／**Claude Agent SDK** を想定した記述） |
| 業務操作の口 | **MCP（Model Context Protocol）**。「AI用の裏口」ではなく、**業務として意味のある操作だけ**を許可した範囲で渡す（対象を探す／根拠を見る／結果を申請する／ログに残す） |
| 業務手順 | **Skill**（`.claude/skills/` 配下のMarkdown）。標準Skillの上に**事業者ごとのSkillを重ねる**。適用順は `CLAUDE.md` / `AGENTS.md` で指示 |
| 本体（変えない） | 業務データ・認証/認可・**承認ワークフロー**・監査ログ。自動架電や書類OCRも本体側 |
| オペレーターの入口 | 自社の Finstage Cowork（ブラウザ上のAIエージェント実行環境。Skill・MCP接続・プラグインを束ね、監査ログとテナント分離を担う） |

**公表されている数値**: ⬛非公開（**削減時間・件数・コストの数値は本文に一切ない**。
唯一の定量的記述は下記の「1回の改善で2週間」）。

**つまずいた点・現状の課題（本文「現状の課題」節）**
- **標準スキルを事業者ごとのプロジェクトにコピーして置いている**ため、標準を直すたびに
  各プロジェクトへ**手で反映**しないといけない。Skill自体に base / overlay の仕組みがまだない。
- スキルの改善は**再鑑の結果を見ながら手で直している**。
- 比較として書かれた一次の定量記述: **業務ロジックを本体（プロダクト側）に埋め込むと、
  判断基準を少し直したいだけでも「精度調査 → 改修 → QA → 本番リリース」の工程が発生し、
  「1回の改善で2週間かかることもあります」**（→ §5）。
