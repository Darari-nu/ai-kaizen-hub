# 規程整備（kitei-seibi）— 社内規程・基準・ガイドラインの型

darariの前職=全社AIガバナンス構築の知見と、ダラリ重工業の実装（2026-08-10体系整備）から抽出した「会社の文書の書き方」。
Kindle教材「ゼロからはじめるAIガバナンス」の実物サンプルを支える型でもある。

## 第0原則: 乗っかる（2026-08-10 darari裁定・Kindleの主張と同じ）

> 「AIの運用は、乗っかれる所に乗っかろうぜ」

**AI独自の文書を乱立させない。既存の基準に織り込む。**

- 会社には既に情報セキュリティ・個人情報・調達・契約・製品開発の文書体系がある。AIはその**新しい1項目**として各文書に入れるのが正しい
- AI独自文書を作るのは、既存文書に収まらない調整事項（体制・審議会・教育）だけ。作る場合も必ず「特則」として親文書（委任元・上位基準）を明記する
- 例: AI入力の可否→情報セキュリティ基準の情報区分に乗っかる／AIサービスの審査→クラウドサービス利用基準に乗っかる／AI搭載製品→製品開発基準のステージゲートに乗っかる／サプライヤーのAI利用→調達の評価シートに1行足す／NDA→AI入力制限の条項を1つ足す

## 最初に分岐: 出口はどっちか

1. **ダラリ重工業モード**（HPの/company/増築）: Astro+`src/components/PortalDoc.astro`。架空明示バナーは共通枠が出す。増築は記事・教材で指すものに限る（「世界を作り込むな、導線を作り込め」）。既存ページの様式は `/company/ai-kitei/` を見本にする
2. **持ち帰り雛形モード**（darari本業・読者用）: 素のMarkdown。**架空会社ネタ・ダラリ重工業固有の記述を混ぜない。会社特定情報（実部署名・実数）を書かない**（RULES.md A1/A2適用）

## 1. 3層の棲み分け（心臓部）

| 階層 | 何を書く | 拘束力 | 改廃の決裁 | 見直し |
|---|---|---|---|---|
| **規程** | 義務・体制・原則（何をしなければならないか） | あり | 社長（審議会経由） | 年1回 |
| **基準** | 具体的な判断表・手続（どう判断するか） | あり | 所管部門長 | 四半期 |
| **ガイドライン** | 推奨・コツ・例（こうするとうまくいく） | なし | 所管部署限り | 随時 |

**判定フロー**: 守らせたいか？ No→ガイドライン ／ Yes→変わりやすいか？ Yes→基準 ／ No→規程

**大原則: 変わりやすいものほど軽い文書に置く。** 重い文書に細かいことを書くと改定が回らず、文書のほうが現実に置いていかれる。実際、改定の大半は書き回しの修正である（darari実感）。ためらわず直し、改定履歴に1行残す。

## 2. 目次の型

### 規程（条文体・である調）

```
第1章 総則      第1条(目的) 第2条(適用範囲) 第3条(定義) 第4条(関連規程との関係)
第2章 体制      責任者・所管部署・審議会
第3章 本則      原則・委任条項(「別に定める○○基準による」)・禁止事項
第4章 教育・調査・報告   教育／実態把握／インシデント報告(自己申告に不利益なし)
第5章 雑則      点検(重要項目に絞る)・改廃(層ごとの決裁を明記)
附則           施行日・経過措置
改定履歴表      年月日／内容／文書番号
```

### 基準（番号見出し・である調）

```
1. 目的・位置づけ   ←委任元の条項番号を必ず明記(「AI利用規程第10条の定めに基づき」)。
                    特則の場合は親基準も明記(「情報セキュリティ基準の区分をAI入力に適用する」)
2. 判断表          表が主役。文章で語らず表で言い切る
3. 手続            申請先・承認者・様式(メール可、まで書く)
4. 迷ったとき      照会先を1つに絞る
改定履歴
```

### ガイドライン（番号見出し・**ですます調**）

```
冒頭宣言: 「べからず集ではなくコツ集。拘束力はここにはない」
1. まずはここから(申請不要の範囲)
2. コツ(具体例の表)
3. よくあるNG集(理由つき)
4. 困ったら(照会先・「相談は怒られません」)
```

### 製品開発基準（ステージゲート型・ISO 9001設計開発の写像）

```
ステージ: 起案 → 企画 → 設計 → 量産準備 → 出荷
ゲート:   DR0    DR1    DR2    DR3       DR4(出荷判定)
各ステージに書くこと:
- ゲートの通過条件(誰が集まり、何が揃ったら次へ進めるか=マイルストーンを明確に)
- 長納期品の着手タイミングを明記(金型はDR2通過後に発注、等)
- ソフトウェアの合流点を明記(企画でアーキ確定・設計で実装・量産準備で検証完了、等)
- AI搭載製品は各ゲートの確認事項を「別表」で追加(起案=発売国/用途/技術の3質問、企画=規制区分の確定、…)
```

## 3. 条文の言い回し規約

- 初出の略称: 「ダラリ重工業株式会社（以下「当社」という。）」
- 列挙: 「次の各号に掲げる」＋（1）（2）…。項は「2」「3」を行頭に
- 義務は「〜しなければならない」、原則は「〜とする」、例外・裁量は「〜することができる」
- 細かい運用メモは（備考）に逃がす。条文本体を汚さない
- 文書番号: 規程=「社規第YYYY-NN号」／基準=「所管略称+基準-001」（例: AI基準-001、情セ基-001）
- 基準・ガイドラインの制定経緯（移設・統合）は改定履歴に必ず書く

## 4. 機械検査（層×文体のミスマッチ検出）

```bash
# 規程・基準ページに「です・ます」混入（ガイドラインは除く）
grep -nE 'です。|ます。' src/pages/company/*kitei*.astro src/pages/company/*kijun*.astro | grep -v guideline
# ガイドラインに条文体の義務表現が混入
grep -nE 'しなければならない|してはならない' src/pages/company/ai-guideline.astro
# 基準に委任元の明記がない（「に基づき」「の特則」「に定めるところによる」がゼロなら疑う）
for f in src/pages/company/*kijun*.astro; do grep -L 'に基づき\|の特則\|定めるところ' "$f"; done
```

いずれも0件（最後は出力なし）が合格。ダラリ重工業モードでは `npm run build` 緑まで確認して push。

## 5. 設計思想集（考え方の正本）

1. **禁止のための規程ではなく、安心して使うための規程**（AI利用規程第1条に明文化済み）
2. **一律禁止よりレベル分け**。一律禁止は現場の判断力を奪い、こっそり利用を生む
3. **審議→基準への昇格ループ**: 基準に無い案件は審議会で決め、繰り返すものは基準に追記して以後の審議を不要にする
4. **自己申告に不利益なし**を明文化する。実態は監視ではなく自己申告で分かる
5. **点検は絞る**: 全部見ない。教育実施率と台帳の有無のような、崩れると全部崩れる項目だけ
6. **改定履歴は1行でいい**。書き回し修正もためらわず改定し、履歴に刻む
