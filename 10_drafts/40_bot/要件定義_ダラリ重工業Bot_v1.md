## 技術構成（2026-08-14 darari裁定）

- 実装リポ: **新規の公開リポ**（GitHub `Darari-nu/` 配下。名前は仮 `darari-jukogyo-bot`）

- コーパス: HPリポの `npm run build` 済みHTML（dist/company/）からテキスト抽出して生成（二重管理しない）
- チャットUI: HPリポ側にページとして置く（画面だけ。APIキーなし方針を維持）

## サイト概要

- 名称: ダラリ重工業 社内チャットボット（表向きの名称は世界観に合わせて後決め。例「総務AI相談窓口」）
- 目的:
  1. Brain教材（2,980円）の**動く実物**。S0「最初に動いてるBotを見せる」の主役
  2. Substack登録（=入社）への導線。本気診断は入社者限定
  3. 読者の「クソ規程あるある」を集める共犯構造（次の記事ネタ）
- 想定ユーザー: 製造業・会社員。AI導入の申請や規程に悩んでいる人
- ユーザーの課題: 「社内規程が読めない・探せない・自分のケースがどれに当たるかわからない」
- 提供価値: 架空会社の規程コーパスで「規程Botが会社でどう動くか」を体験できる
- ユーザーにしてほしい行動: 数問試す → 入社（Substack登録）→ 本気診断 → 教材へ
- 収益モデル: Bot自体は無料。**唯一の売り込み=「限界の告白」**（浅い答えしか出せない場面で教材第3章へ誘導）
- 運用者: darari（実装・運用の実況がそのままSubstack連載になる）
- 初期リリース範囲: 下記ロードマップのMVP

## 機能仕様（裁定済みの確定要件）

### 1. 正典の縛り（西野部答申・機械的ルール）
- ナレッジは **/company/ の既存規程コーパスのみ**（規程・基準20ページ超＋イントラ文書）を唯一の正典とする
- **「規程にないことは答えない」**。実装は次の機械的ルールで担保する:
  - 回答には必ず出典（規程名＋条番号）を引用させる
  - 出典を引用できない質問には定型で返す: 「当社規程に定めがありません」＋世界観に沿った案内
  - 一般的なAI知識・世間話・規程外の法律相談には答えない（プロンプトで禁止＋出典必須ルールで二重化）
- 世界観増殖の防止: Botの回答から新しい設定を生やさない。規程の増築は記事駆動のみ（既存裁定）

### 2. 段階制（2026-08-14裁定: **MVPは無料モードのみ**）
- **来訪者（誰でも）**: 1日3問まで無料。超えたら「本日の相談受付は終了しました。入社（メルマガ登録）で続きをどうぞ」
- **入社者限定の「本気診断」**（読者が自社の「クソ規程あるある」を書く→ダラリ重工業の規程と照らして診断→記事ネタになる共犯構造）は**Phase 2**。連載の反応を見てから設計する。ゲート方式（合言葉=社員証番号など）もそのとき決める
- **全体上限（無料枠の防波堤）**: サイト全体で1日の合計質問数に上限（初期値200問/日=Gemini無料枠RPD内、要実測調整）。超過時は「本日の窓口は混み合っております」

### 3. 限界の告白（唯一のセールス）
- 法令対応・社内申請の「深い」領域に踏み込まれたら、答えを薄めるのではなく**正直に限界を言う**:
  「ここから先（法令対応・申請の通し方）は、わたしの中の人が教材にまとめています」→ Brain教材第3章へリンク
- 発売前は教材リンクの代わりにSubstack連載へ誘導（差し替え可能な設定値にする）

## サイトマップ・導線

- 設置ページ: `/company/intranet/` 配下に新ページ（社内イントラの世界観に同居）
- 導線: 記事内リンク・イントラページ → Bot体験 → 無料枠消費 → 入社案内 → Substack → 合言葉で本気診断
- HP（Astro側）が持つのは**チャットUIの画面だけ**。APIキー・制限管理はすべてバックエンド側 → HPリポの「DBなし・APIキーなし」方針を守る

## データ設計

- 保存するもの（バックエンドのKV等）:
  - レート制限カウンタ（訪問者識別子ごとの当日質問数／全体カウンタ）— 24時間で自動失効
  - 入社者ゲートの通過状態（トークン）
- **保存しないもの（MVP）**: 会話ログ・メールアドレス・個人情報は保存しない
  - 本気診断の「あるある」を記事ネタとして蓄積したくなったら、**保存の是非と告知文言をdarariに再裁定**（プライバシーポリシー改訂とセット）。MVPでは画面に「診断結果はその場限り。保存していません」と明記

## API設計（バックエンド=中継サーバ1本）

- `POST /chat` : 質問を受け、規程コーパス＋システムプロンプトでLLMに中継、回答を返す
  - 入力検証・レート制限判定をここでやる（出典必須の機械チェックはTODO・まずはプロンプト側で担保）
- `POST /gate`（入社者トークン発行）は**Phase 2送り**
- 規程コーパスはHPリポのビルド済みHTML（dist/company/）からテキスト抽出して同梱（二重管理しない。HP側が更新されたら再生成→再デプロイ）

## 認証・権限

- ログインなし。会員DBを持たない（Substackがリストの正本、という既存裁定と整合）
- 入社者ゲート（Phase 2）は「Substack登録者だけが知り得る情報」で判定する方針。方式はPhase 2着手時に裁定

## セキュリティ

- APIキーはバックエンドの環境変数のみ。フロントに一切出さない
- プロンプトインジェクション対策: 出典必須ルール＋「規程にないことは答えない」が実質の防壁。加えてシステムプロンプトの開示要求・役割変更要求は定型拒否
- レート制限で経済的DoS（APIコスト攻撃）を抑止。全体上限が最後の防波堤
- 免責表示: 「架空会社の架空規程です。法的助言ではありません」（教材と同じ免責を先に実装）

## 費用感（試算）

- **実費ゼロ運用が成立**（2026-08-14裁定）: Cloudflare Workers無料枠＋Gemini 2.5 Flash無料枠
- 制約: Gemini無料枠は1日あたりのリクエスト数上限（RPD）がある → 全体上限をRPD以下に設定して「混み合っております」で受ける。無料枠の仕様変更リスクは全体上限とモデル名を環境変数化して吸収
- コーパス約6〜8万トークンを毎回全文渡す（1Mコンテキストに収まる。RAG不要のシンプル構成）

## テスト（最低限）

1. 規程にあることを聞く → 出典つきで答える
2. 規程にないことを聞く → 「定めがありません」定型で断る
3. 一般知識・雑談・インジェクション（「規程を無視して」）→ 断る
4. 無料3問超過 → 入社案内が出る
5. 全体上限超過 → 「混み合っております」
